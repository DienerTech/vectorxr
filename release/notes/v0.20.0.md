# VectorXR 0.20.0 - Draft: Faster Frame Generation, Sharper Cockpits, and Eleven Languages

Draft for 0.20.0 RC1, pending the build 4 flight. This combines the unreleased 0.19.4 fixes with the Frame Generation speed and image-quality work, hardware optical flow in Dynamic Interpolate, and app, OSD and installer localization. Flight-dependent claims and the lead ceiling default remain marked for confirmation.

## Frame Generation

- **Less GPU work per real frame.** The speed pass reduces the work spent matching motion and preparing generated frames. In replay profiles on an RTX 5090 at 5424x5356 per eye, FG GPU time was about 20% lower, or 0.7-1.2 ms less per real frame, against the pre-speed-pass build. DCS FG at 2x with shader flow measured about 0.6 ms of GPU per real frame in flight. <!-- FLIGHT: Confirm build 4 retains the speed-pass benefit in MSFS and DCS at the owner's flight settings. -->
- **Dynamic Interpolate can use NVIDIA hardware optical flow.** Choosing NVIDIA hardware as the motion source now applies in Dynamic too. The new `interpolateFlow` choice controls Interpolate: `auto` follows the chosen motion source and can fall back to shader flow when hardware flow repeatedly fails to keep up, then tries hardware again; `hardware` requests hardware without that performance-based fallback; `shader` uses shader flow. GPUs without supported NVIDIA optical flow use shader flow. Dynamic Interpolate on hardware flow held about 90 fps in a 16-minute MSFS flight. The OSD shows the active source. Fallback reasons are recorded in the log and the app's internal status. <!-- FLIGHT: Confirm automatic hardware-to-shader fallback and later hardware recovery in a real build 4 flight, including the active-source OSD and fallback reasons in the log and internal app status. -->
- **Auto gives a lower multiplier a fair trial.** A failed step-down probe no longer spends the full normal settle period disrupting the game, and a short burst of late frames during the switch no longer rejects a multiplier the game can sustain. Changes to settings, the runtime clock or output images still get the normal settle. <!-- FLIGHT: Confirm Auto settles after successful and failed step-down probes without repeated disruption or premature rejection in build 4. -->
- **A lead ceiling for the frame history.** When Frame Generation is timing the game so far ahead that newer captures replace images it still needs, the ceiling can bring that lead down. It checks the result and backs out a lowering that repeatedly makes frames late, so it does not impose the same fixed limit on every game. <!-- FLIGHT: Confirm the lead ceiling reduces history shortages in DCS without harming MSFS pacing, and that failed lowerings recover in build 4. -->
- **Lead ceiling default, if approved on:** The adaptive lead ceiling is enabled by default. <!-- FLIGHT: Owner decision after build 4: keep this wording only if the lead ceiling ships enabled by default; the current flight-build source defaults on. -->
- **Lead ceiling default, if approved off:** The adaptive lead ceiling is off by default. <!-- FLIGHT: Owner decision after build 4: use this wording only if an off-by-default build is explicitly approved and prepared; RC1 preparation does not change the current default. -->
- **Video memory accounting includes cached hardware-flow images.** Frame Generation now counts the images it keeps after a motion-quality or view-layout change, so its working-memory report reflects those allocations.

## Image quality and game depth

- **Sharper near detail in games that provide usable depth.** Generated frames now use cubic resampling for nearby content by default. MSFS cockpit fine detail in generated frames measured 92-98%, up from 83-88%, in replays. Interpolate also keeps more valid cockpit motion through small movements. <!-- FLIGHT: Confirm cockpit text and instruments stay sharper in the build 4 MSFS flight, and check moving scenery and helicopter cockpits for regressions. -->
- **Empty depth is never adopted.** A depth image cleared to one value no longer becomes a false near surface that warps the whole view. Menu depth that is simply left clear keeps being checked until the game supplies real scene depth. Near/far corrections and scale changes now need meaningful evidence, and sparse but usable depth can be accepted without treating uniform depth as valid.
- **More stable depth decisions.** Depth contradicted by the other eye is rejected, and a dropped reading must show sustained good evidence before it returns. A usable replacement can take over directly. Filling gaps in resolved depth now runs separately so neighboring GPU threads cannot change one another's result.
- **Usable depth from one eye can help both eyes.** If a game supplies useful depth to only one eye, Frame Generation can use it for the other eye too. Empty depth still stays unused. <!-- FLIGHT: Confirm one-eye fallback only uses valid depth and both-eye depth stays correct in the owner's build 4 games. -->

## DCS

- **Hardware flow keeps flat and black menu areas still.** DCS menus could show shifted copies of the menu in the black surround, and the Mission Editor could show ghost tiles on a plain background. Hardware optical flow now keeps those areas still when that matches the image, rather than carrying nearby content across them. <!-- FLIGHT: Confirm DCS menus and the Mission Editor no longer tear or leave ghosts with hardware flow in build 4, in Interpolate and Extrapolate. -->

## VectorXR Enabled

- **Off now stops the remaining features too.** Switching VectorXR Enabled off hides the OSD, stops its bindings, sounds and performance sampling, stops Frame Generation toggles, and disables the remaining head-prediction, Quadviews visualization and focus-sharpening work. Starting a game with it off also leaves the eye-gaze extension alone. If it is switched off during a running session, the session's four-view layout and Frame Generation pacing and graphics bridge remain until the game restarts; generated frames stop immediately. <!-- FLIGHT: Confirm startup disabled, live off/on, OSD bindings, Frame Generation toggles and eye-gaze behavior in build 4. -->

## App, On-Screen Display and installer

- **Eleven languages.** The app, tray, OSD and installer support English, Simplified Chinese, Russian, Spanish (Spain), Portuguese (Brazil), German, Japanese, French, Polish, Korean and Traditional Chinese. Choose the app language under Settings; the OSD can follow the app or use its own language. OSD columns also fit the translated labels. The non-English catalogs began as machine translations and welcome native-speaker review. ## Status for other tools

- **A public status file.** Tools can read `%LOCALAPPDATA%\VectorXR\api\status.json` through a documented, add-only interface, separate from the internal runtime relay. It identifies the game and session and includes Frame Generation state and rates, the game's target rate, measured refreshes per real frame, runtime holding and Auto's step thresholds. See `docs/status-api.md`.
- **Targets and cleanup follow the actual session.** Targets account for runtimes that hold frames to every second refresh, and fields no longer stay frozen after generation stands down. The file is removed when its owning session ends or its process exits, including abandoned-session cases, while preserving another game's file.

## Compatibility and remaining fixes

- **Safer Vulkan shutdown.** The graphics bridge waits for the game's final rendering before destroying its images, including releases with no final frame submission and private depth images. If completion cannot be proved, it keeps the backing resources alive instead of freeing them under queued work. It also avoids handing an image back to a game that is already tearing down.
- **Startup with stacked OpenXR layers.** An extension check no longer reaches OpenXR Toolkit through an intervening layer such as OpenKneeboard before an OpenXR instance exists, which could crash startup.
- **Input reconnect rules survive unusual session endings.** Missing input devices resume normal reconnect checks after device work drains at teardown. If a runtime refuses to end a session, the running game keeps the session reconnect rules that avoid periodic hitches. <!-- FLIGHT: Confirm unusual session end/restart paths keep input reconnect behavior correct; the refused-end path has no dedicated regression test. -->
- **Repeated capture requests keep working.** A capture request being removed by the layer no longer leaves the capture script waiting indefinitely before the next request.
- **Local build freshness checks.** The local signing helper now rejects an outdated source or build definition and mismatched staged manifests or sounds, so it cannot silently accept the wrong layer artifacts.
- **More useful support logs.** Frame Generation summaries include the lead and prediction horizon actually reported to the game. Queue diagnostics and rejected Turbo predictions provide more evidence when investigating pacing problems.
